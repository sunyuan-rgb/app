# 阅读活动跨环节一致性检查（题目 10 业务专项）

## 用途

检查"事件接入 → 进度去重 → 达标发奖 → 申诉补发"各环节业务约束是否被正确实现，并用数据库查询产出可归档的证据，防止：重复计文章、错误归日、重复发奖、客服越权改数、迟到窗口漏判。

## 触发场景

- 事件接入、进度、发奖、申诉相关代码变更之后（开发自检）。
- 测试设计前，确定必须覆盖的约束点。
- 运营/客服核查发现疑似不一致，需要定位被破坏的约束。

## 输入

- 已配置连接的业务数据库（默认 `reading_activity`，容器 `dev-mysql`）。
- 可选：指定 `user_id` 与 `biz_date`，缩小核查范围。

## 执行步骤

1. **代码层检查**（逐条给结论 + 文件:行号证据）：
   - 事件合法性：鉴权；event_id 全局唯一；同编号不同内容被拒绝且写入 `event_conflict`；发生时间 ∈ [活动开始, 结束]；发生时间 ≤ 接收时间；接收 − 发生 ≤ 24 小时。
   - 业务日期归属：`biz_date` 按发生时间的北京时间计算；跨日迟到归发生日；活动结束后窗口内事件仍入账。
   - 去重：唯一键 `(user_id, biz_date, article_id)` 存在于迁移 SQL；应用层不得仅靠内存判断。
   - 发奖幂等：唯一键 `(user_id, activity_id, biz_date)`；奖励记录 + 积分流水 + 余额更新在同一事务；客服补发复用统一发奖路径。
   - 申诉合规：客服无直接改余额/改原始事件的代码路径；同用户同日仅一条未结申诉。
2. **数据层检查**：执行 `scripts/consistency_queries.sql` 中的全部查询，逐条记录结果。
3. **交叉核对**：比对"当日达标人数"（按去重后有效文章数 ≥3）与"发奖人数"（reward 行数），两者应一一对应；余额 = 流水合计。

## 输出格式

```text
检查结论：通过 / 不通过 / 有风险
代码层逐项：[约束点] → 通过/不通过 → 证据（文件:行号）
数据层逐项：[查询编号 Q1~Qn] → 结果摘要 → 是否一致
问题清单：违反约束、位置、影响、建议修复方向、是否阻塞
```

## 失败处理

- 任一阻塞项（发奖幂等、归日错误、余额与流水不平）不通过 → 标记"不通过"，禁止进入验收。
- 无法取证的项标记"待人工确认"，不得自行判定通过。
- 数据库不可达时终止数据层检查，输出已完成的代码层结论。

## 完成标准

代码层 5 组约束、数据层全部查询均有结论与证据；阻塞项清零；结果归档至 `docs/evidence/` 对应任务编号目录。
